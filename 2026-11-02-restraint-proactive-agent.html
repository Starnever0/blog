设计草案 · 非产品宣传 · v0.1

克制
——一份主动式助手的设计草案

AI 缺的不是智能，是克制。这份文档讨论的不是"如何让助手更主动"，而是"如何让它在绝大多数时候保持沉默，只在极少数时刻开口"。

性质 方向草案，非产品规划 形态 开源设计 + 最小实现 日期 2026-11-02

阅读前须知（这是本文最重要的部分之一）。

文中所有延迟、功耗、成本数字，均来自公开资料或按典型场景推算，无一项经本项目实测。本文不主张这些数字准确，只主张它们量级可信、足以支撑架构取舍。

本文也不主张这个设计是对的。第 06 节完整列出我们已知的、尚未解决的局限；第 07 节列出明确不做的范围；第 11 节列出仍然悬空的决策。如果一份设计草案只写"我们能做什么"，它就不是草案，是宣传。

01 / 命题

现在的 agent 都是"被叫醒的"，这既是它的优点，也是它的天花板

从 ChatGPT 到各类 coding agent，主流交互范式是同一个：用户形成意图 → 构造请求 → 系统响应。这个范式极其成功，但它有一个结构性前提——用户必须先知道自己需要什么。

而现实里大量损失发生在相反的情形中：当事人根本没想到要问。老人不知道这通电话是诈骗，购物的人不知道账算错了，谈判的人不知道对方报的价是市场价的三倍。在这些时刻，"没有意图"本身就是问题所在。

于是有了"主动式 agent"这个方向：让它一直在场，自己判断何时介入。听起来是自然演进，但历史上这条路死过很多次：

尝试形态失败原因（我们的判断）
Microsoft Clippy桌面助手，基于规则触发提示触发条件与"用户需要"无关，只与"系统检测到模式"有关
Google Now基于位置/日程主动推卡片信息相关，但不改变决策，最终沦为噪音源
各类"智能推荐"行为预测后主动推送优化目标是点击率，不是用户的决策质量
Always-on 录音硬件Plaud NotePin / Limitless Pendant解决了"记录"，没有解决"何时开口"——所以它们本质是录音机

这些失败有一个共同点：它们不是在"能力"上失败，是在"判定标准"上失败。系统能检测到很多东西，但没有一个标准能回答"此刻是否值得打断这个人"。

主动式 agent 的核心难题从来不是"能不能感知"，而是"凭什么开口"。
前者的成本每年下降一个数量级，后者十年没有进展。

所以本文提出的命题是：主动式助手的竞争力不在能力侧，在克制侧。一个能准确判断"现在不该说话"的系统，比一个能回答一切问题的系统更难做，也更有价值。

02 / 判据

什么算"该提醒"：从相关性判断换成后果判断

最直觉的判据是："如果我知道用户不知道的信息，就告诉他。"这个判据一用就崩——因为几乎每一句话背后都存在用户不知道的信息，"该提醒"的集合是无限的，系统会在每一秒都想开口。

更精确的判据来自一个观察：用户自己上网搜索完全能获得同样的信息，他不搜，不是因为搜不到，是因为没想到要搜。所以真正的稀缺不是信息，是"意识到此刻需要一个判断"。

判据：这条信息会不会让他改主意

把"用户是否需要额外信息"换成"这条信息是否会改变他的选择"，性质就变了：前者是相关性判断（永远为真，无边界的）；后者是后果判断（有限、可枚举、可测量）。

对话片段是否相关是否改变决策该不该开口
"今天去野营还是踏青啊"是（可推荐）否不该
"明天应该挺凉快吧"（实际 25℃，舒适）是否不该
"不知道明天会不会下雨"（实际 78% 降雨）是是该
"那就这么定了，明天野营"（未察觉降雨）是是该（隐式缺口）

注意表格后两行：第三行用户自己说出了信息缺口（"不知道会不会下雨"），这属于显式缺口，判定极容易；第四行用户已经拍板，缺口是隐式的，需要系统自己意识到"这个决定依赖一个他并不掌握的信息"。

这两行的难度差一个量级，而产品价值几乎全部在后者。显式缺口只是"更快地搜索"，隐式缺口才是"他想不到要问"。本草案的立场是：v1 只做显式缺口 + 高确定性阻断，隐式缺口是长期目标，不是当前承诺。

由此派生一个指标：决策翻转率

如果判据是"会不会改主意"，那么系统的质量就可以直接度量——在所有触发的提醒中，有多少真的改变了用户的行为。这个指标比"准确率"诚实得多，也更难伪造：

示例口径

某次评估共触发 12 次提醒：其中 9 次用户在提醒后改变了原定动作（未转账 / 改期 / 复核账单），2 次用户表示"我知道，但没关系"，1 次被判定为噪音（提醒内容与场景无关）。

→ 决策翻转率 9/12 = 75%，噪音率 1/12 = 8.3%。

这个指标有一个副作用值得提前说明："改变了行为"并不总是好事。如果用户本来是对的，AI 把他劝错了，也算一次"翻转"。所以它必须和人工复核配对使用，不能单独作为优化目标。这一点在第 06 节会再提到。

03 / 机制

四级漏斗：让模型做判断，但别让模型做路由

最初的想法是"用一个轻量模型随时判断是否需要帮忙"，大多数时候它判定"不需要"，于是不执行任何动作来省算力。方向是对的，但有一个隐藏成本：判断本身就要花算力。省掉的是执行，不是判断。让一个 1B 模型常开跑二分类，功耗和误报都会失控。

正确的形状不是"一个模型做路由"，而是一条逐级变窄、逐级变贵的漏斗——越往下，被处理的样本越少：

L0
声学门控VAD 能量检测 + 热词/关键词唤醒。不做语义判断，只回答"有没有人在说话、有没有出现候选词"。
~1 mW
常开
L1
事件抽取（不是转写）端侧流式 ASR + 结构化抽取。输出的是事件，不是文本：谁、说了什么类型的话、涉及多少金额、是否构成承诺或要求。
~50 mW
唤醒后
L2
判定：是否改主意唯一需要真正推理的一层。输入是事件而非全文，输出是 silent / alert + 置信度 + 理由。
按需调用
一天数十次
L3
策略与话术用什么通道（耳语/震动/卡片）、说多长、什么语气。纯规则，不花算力。
无模型

关键设计：要不要听由 L0 的事件触发决定；值不值得说由 L2 决定。模型不负责"要不要看"，只负责"这个事件值不值得开口"。

事件 schema：真正的复用点

如果将来要扩展场景，"通用性"不会从场景堆叠里长出来——五个场景共享的只是 L0 和 ASR，L2 的判定、L3 的话术、数据源，每个场景都完全不同。所以复用的唯一机会在中间层的事件格式：把事件类型做成可扩展的插件，而不是硬编码。

// L1 输出：事件，而非文本
{
  "type": "authority_claim",   // 可枚举，可扩展
  "speaker": "other",          // 谁说的，判定命门
  "content": "要求转账至安全账户",
  "entities": { "amount": 123000, "object": "bank_account" },
  "confidence": 0.87
}

// L2 输出：沉默是一等公民
{
  "action": "silent",  // silent | alert —— 必须显式
  "reason": "出现资金动作，但用户尚未表示同意",
  "flip_potential": 0.4     // 是否可能改主意的估计
}

// L3 输出：一句，不长
{ "text": "别转。真警察不会让你转钱。", "channel": "whisper" }

注意第二段里的 "action": "silent"。沉默必须是一个正式的输出状态，并且带理由，不能实现成"没触发所以没有输出"——那样沉默就从日志里消失了，而沉默恰恰是这个系统最重要的行为。

以上为手工构造的演示数据，非实测。真实系统在这一段里的判定错误率、延迟分布均未知。

为什么在第 8 句（"转到安全账户"）不开口，非要等到第 10 句？

这是本设计里一个反复权衡过的取舍。第 8 句首次出现"转账"动作，风控意义上已经越线，但从"是否改主意"的角度看还差两样东西：金额未知、紧迫性未知。此时开口，很可能得到"哦，我问问多少钱再说"——提醒到达了，但没有改变任何决定。

第 10 句补齐了三个要素：具体金额（十二万三）、时限压力（下午五点）、威胁（通缉令）。这三个要素同时出现的时刻，正是用户即将从"听"转向"做"的时刻——也就是决策窗口的最后边缘。

代价是：如果用户在这之前就已经打开银行 App，我们就晚了。这类漏报在本设计中被接受，因为漏报的代价是一次没帮上，误报的代价是信任崩塌。这个不对称是整套架构的伦理前提，不是优化参数。

如果提醒发出去了，用户还是转了钱，算什么？

算一次"未翻转"，不算系统失败，也不该被消化成"准确率"问题。这类案例恰好说明：提醒到达 ≠ 决策改变。本设计在 fixture 里专门保留这类样本，并且明确区分两个指标——判定准确率（判定对不对）和决策翻转率（提醒有没有用）。

把这两个指标混在一起，是这类产品最容易自欺的地方。

05 / 核算

三笔账：延迟、功耗、成本

这一节是为了回答"这可行吗"。结论是：端侧判定可行，开放式联网查证不可行。三笔账分别是延迟（体验）、功耗（形态）、成本（商业）。

第一笔：延迟——卡点不在生成，在检索

"既然用户自己搜索很快，为什么 agent 不行？"这是个好问题，答案是慢的地方和想象中不一样：

环节典型耗时说明
判定"该不该查"300–800 ms若用 LLM 就要付这一次
构造 query（消歧）300–1000 ms被低估的大头：哪个城市、哪一天、"下雨"用什么阈值
网络往返50–800 ms弱网更差
搜索 API300–800 ms
抓正文 + 清洗1000–3000 ms真正的瓶颈
生成一两句300–500 ms确实不慢
端到端3–6 s（最坏 10 s+）生成只占约 1/10

更关键的不是毫秒，是"构造 query"这一步。用户搜索跳过了"理解意图"，agent 必须付这个成本；而这一步错一次，后面全废。

构造 query
0.3–1.0s
抓正文清洗
1.0–3.0s
L2 判定
0.3–0.8s
生成
0.3–0.5s
端侧规则链
<0.2s

所以产品形态上必须做一次切割：

能做实时（<1s）

算术校验、单位换算、常识判断、可预取的结构化数据（天气/汇率/股价/号码黑名单）。前提是数据源可枚举、可提前拉取。

做不到实时（3–6s）

开放式联网查证：需要读网页再总结的那一类。只能退化成"决策窗口内的补充"，接受延迟，落在用户拍板之前即可。

这个切割反过来强制了场景垂直：想要实时，就必须把可查的信息限制在"可预取的数据源 + 端侧知识"；想要开放搜索，就必须接受秒级延迟。两者在架构上互斥。

第二笔：功耗——刚好一天，没有余量

组件功耗占空比日均等效
VAD / KWS 常开~1 mW100%1 mW
端侧 ASR~50 mW~20%10 mW
NPU 事件抽取~200 mW~5%10 mW
蓝牙 + 偶尔上行~5 mW100%5 mW
合计~26 mW

按挂坠形态 300 mAh / 3.7 V（≈1.1 Wh）计算：约 40 小时理论值，工程余量打对折后约 17–20 小时。刚好一天，没有余量。

这直接否掉了眼镜形态——主流 AI 眼镜重负载续航只有 3–5 小时，装不下"常开 VAD + 蓝牙常连"这套组合。而耳机 + 充电盒能整天循环供电，且耳机是天然私密通道（只有用户听得到），符合"提醒不该被第三方听到"这条硬约束。

第三笔：成本——云端 ASR 一项就能击穿订阅模型

按每天 8 小时对话场景估算（实际有效语音约 4 小时，≈4.8 万字）：

方案日流量月度成本（估）结论
音频全量出端 + 云端 ASR≈115 MB/天≈¥72/月单这一项就超过 30 元订阅费
端侧 ASR，只上行事件文本KB 级≈¥3–5/月可行

（按 ¥0.3/小时 ASR 市价与 32 kbps 音频码率估算。）

所以端侧化不是性能优化，是商业模型能不能成立的前提。"算力限制""电力限制"不是待解决的问题，是架构的输入条件。

06 / 局限

局限与约束：我们已知但没解决的

这一节是本草案的主体之一。以下每一条都是设计上的真实缺口，不是"未来会优化"的委婉说法。标注为未解的，意味着当前没有可行方案。

01

延迟：开放域实时插话做不到 未解

开放式联网查证端到端 3–6 秒，而对话中的"黄金窗口"往往只有两三秒。这不是工程优化能填的差距，是链路结构的必然结果。本草案的应对是改变产品形态（决策纠正而非实时打断），而不是假装能解决。

02

数据：比价类需求无解 未解

"这个报价是否高于市场价"不是推理题，是数据题。长尾商品的价格库无法覆盖，且"市场价"本身模糊（同一件衣服商场与批发市场差数倍）。本草案承认这一整类场景不可做，而不是用 LLM 猜价格。

相对地，"金额算错"是可判定的：对话里有单价、数量、总价，做算术校验即可，接近 100% 精度、零外部依赖。同一个"购物助手"里，这两个子功能的可行性差一个数量级。

03

精度：端侧判定模型的天花板未知 未解

1B–3B 级端侧模型在自由对话流上做"是否改主意"的主观判断，精度能到多少，本项目没有实测数据。这是整个设计最大的未知量，也是"能跑的最小实现"首先要回答的问题。

已知的是方向性约束：误报代价远大于漏报，所以系统必须往 precision 极度倾斜，宁可漏。代价是 recall 会很难看。

04

合规：常驻录他人对话 未解

涉及《个人信息保护法》与《民法典》隐私权。技术上能做的规避只有三条：音频不出端、不留存原文、明确告知。但这三条只能降低风险等级，不能消除——因为在他人不知情的情况下持续收音，本身就处在灰色地带。

本草案的立场：演示与开源阶段全部使用合成语料，不涉及真人录音。这是边界，不是过渡方案。

05

记忆：短窗口丢失跨时段叙事 部分可解

当前设计只用滑动短窗口，进入新场景即丢弃前文。这换来了三个好处（无合规风险、无检索质量问题、无状态污染），但代价明确：真实诈骗往往分阶段推进（建立信任 → 试探 → 分步要钱），可能跨几天、跨多通电话，短窗口接不住。

可能的补丁：不存对话，只存"事件摘要"（谁、何时、涉及什么动作、多少金额），几十字节的结构化字段。隐私上依然干净，但跨时段线索得以保留。此补丁尚未验证。

06

输入：本草案不含 ASR 范围外

v1 的输入是预先构造的、带说话人标签的口语转写稿。真实 ASR 的错字率、抢话、方言、噪声、说话人分离错误，全部未覆盖。

这是一个刻意的裁剪：ASR 是成熟件，做出来不加分，做砸了毁演示。但必须诚实说明——本草案验证的是"判定链路"，不是"完整的语音产品"。

07

评估：没有 ground truth 未解

"这一句本该提醒但没提醒"没有任何自动标注手段。只能靠人工写 fixture、人工标注、人工复核。样本量注定很小（数十段对话），统计意义有限。

更麻烦的是决策翻转率：它需要知道用户"本来会怎么做"，而这只能通过追问或推断获得，本身就有偏差。

08

伦理：提醒会把人推到选边站的位置 未解

如果老人正信任那个销售，AI 说"这是骗人的"，老人面临的是一个二选一：信 AI 还是信眼前这个人。实际结果常常是更抗拒 AI。

由此派生一条反直觉的推论：给老人调高出言频率，会加速被嫌弃。老人最反感的不是 AI 说错，是被当小孩管。这条约束直接否掉了"用更高频次表达关怀"的产品思路。

07 / 边界

明确不做：这些不是待办，是排除

一个设计草案的可信度，很大程度上取决于它敢不敢列"不做"。以下是本草案的排除清单——其中每一条都曾被讨论过，然后被主动放弃：

不做理由
通用助手判定边界无法收敛，"该提醒"的集合变成无限
比价 / 市场价判断数据不可得，且"市场价"本身模糊（见 06-02）
会议纪要产品该赛道已有成熟玩家，且与"提醒"的功耗/延迟需求互相冲突
长期记忆合规风险与检索质量问题远大于收益；只保留事件摘要补丁
ASR / 发声 / UIv1 范围外，属于"不加分但可能毁演示"的部分
儿童场景伦理风险高于价值，且涉及《未成年人网络保护条例》的额外约束
眼镜形态电池装不下常开链路；且眼镜是"给别人看的"，与私密提醒相悖
08 / 场景

场景矩阵：技术的可行性 × 政策的契合度

判定确定性是硬约束（决定能不能做），政策与付费方决定值不值得做。两者交叉后，真正值得作为主线的场景很少：

场景确定性政策依据付费方定位

三圈交集（技术可判定 + 政策有明文 + 付费方清晰）只有三个：老人反诈、陪同就医、用药安全。而且这三个可以共用同一个硬件与同一套 L1 事件 schema——它们不是三个产品，是同一件事的三项能力。

"演示支线"里的场景（购物算错账、天气决策）承担的是另一个职责：在演示里讲清"主动提醒"这个机制有多惊艳，但不承担长期叙事。这个分工必须提前说清，否则很容易把最上镜的场景误当成主线。

09 / 演进

通用性来自抽象层，不来自场景堆叠

一个常见的设想是：先分别做多个垂直场景，等它们长出来再合并，最终得到通用助手。这条路我不认为成立，原因很具体：

五个场景共享的只有 L0（VAD/KWS）和 L1 的 ASR——这两层本来就是通用的。而 L2 的判定逻辑、L3 的话术、依赖的数据源、事件类型的枚举，每个场景完全不同。把五个场景各做一遍，得到的是五个并行的垂直产品，不是一个通用助手。它们之间不会自动合并，只会共享一个外壳。

通用性不是"合并"出来的，是"抽象"出来的。

所以路径应该是反的：v1 只做一个场景，但那个 event schema 要按"将来有二十个场景"来设计——事件类型是插件，不是硬编码；L2 吃统一的事件格式，不关心事件来自哪个场景。这样加场景是加插件，不是重写。

阶段目标判定标准
v0.1 最小链路单场景（老人反诈）、fixture 输入、跑出 precision 数字precision ≥ 90%，且失败案例被公开列出
v0.2 插件化第二、第三个场景接入，不改 L1/L2 主干新增场景不修改 schema 结构
v0.3 端侧ASR + 事件抽取跑上真实硬件功耗账与延迟账被实测复核
v1.0 形态完整含发声、含形态、含真实环境测试决策翻转率在真实场景中被独立测量

每个阶段的门槛都是数字，不是"做完了"。这是为了防一件事：这类项目最容易在 v0.1 就停下来讲愿景，因为讲愿景比跑数字舒服得多。

10 / 形态

开源形态：交付物不是一份文档，是一个能跑的最小实现

如果这个项目的目标是让行业相信这件事该有人做，那么参照物不是产品发布会，是那些能被 git clone 下来直接跑的仓库。这类项目带节奏的原因从来不是文档写得好，是代码能跑、数字能复现。一个只有架构图的仓库，会被归进"又一个 idea"。

所以交付物有两个，职责必须分开：

网页（本文）

读者是路过的开发者和研究者。目的：让人相信这件事该有人做。内容：命题、判据、难点、三笔账、沉默可视化。

仓库

读者是想 clone 的人。目的：让人相信你真的做了。内容：fixture、schema、评测脚本、跑出来的数字、以及失败案例。

"能跑"的验收线

不是功能完整，是能出一个数：

$ python run.py --fixture anti_fraud_01
─────────────────────────────────────────────
  fixture          anti_fraud_01  (18 turns)
  alerts fired     1 / 18 turns
  precision        0.92
  recall           0.67
  decision flip    1 / 1
  ─────────────────────────────────────────────
  missed:  turn 6  "不能跟家里人说"  (isolation tactic,
           judged silent — 见 FAILURES.md#f-003)
  false:   turn 11 "转账" (正确判定为非诈骗，但话术过重)

注意最后两行——开源项目最忌讳"全部通过"。一个把误报案例列出来、并写清"我在哪一步判错了"的 README，可信度远高于一个宣称 100% 的仓库。而且这恰恰是本文想论证的核心：这件事的难点在 precision，不在能力。

仓库结构（拟）

restraint/
├── schema/
│   ├── event.schema.json      // L1 输出，可扩展插件
│   └── verdict.schema.json    // L2 输出，silent 是一等公民
├── fixtures/
│   ├── anti_fraud_01.json     // speaker + text + t + 标注
│   └── README.md              // 标注口径说明
├── pipeline/
│   ├── extract.py             // L1 事件抽取
│   ├── decide.py              // L2 判定
│   └── speak.py               // L3 话术
├── eval/
│   └── run.py                 // precision / recall / flip rate
├── FAILURES.md                // 我们判错的案例，逐条
└── README.md

设计上有一条硬规定：fixture 里必须带 speaker 标签。因为"这句话是谁说的"是判定的命门——"转钱到安全账户"若是对方说的才是诈骗信号，若是老人自己复述的，性质完全不同。用不带 speaker 的干净书面文本做测试，等于在一个真实世界不存在的输入上调试。

11 / 未决

仍然悬空的问题

这一节存在的原因很简单：如果一份草案没有任何未决问题，说明它没被认真想过。以下每一条都会实质影响架构，且目前没有答案。

  • 端侧判定模型具体选哪个？1B 级还是 3B 级、量化到什么精度、在什么芯片上跑——这个决定直接决定功耗账能不能成立。目前悬空。
  • 事件 schema 的粒度定在哪？太粗会漏（"资金动作"盖不住"承诺"和"威胁"的差别），太细会让 L1 的抽取精度崩掉。这个平衡点要靠实测找。
  • 话术风格由谁定？"别转，真警察不会让你转钱"这句话的语气，可能比判定准确率更决定用户是否采纳。而它目前是拍脑袋写的。
  • "不提醒"的默认值是否需要用户可调？如果用户嫌吵调高阈值，precision 上升但 recall 下降；这个开关放不放给用户，涉及产品哲学。
  • fixture 怎么造才不失真？手写会过于规整，真人念又受限于合规。目前倾向"真人念一遍再用 ASR 转出来"，但未验证。
  • 决策翻转率怎么测才算数？问用户"你本来会怎么做"必然有回忆偏差；观察行为又受限于演示环境。目前只能靠人工复核。
  • 这套东西在多大程度上依赖"特定语言的特定话术"？如果事件 schema 高度依赖中文诈骗话术，那"通用性"这个叙事就要打折扣。
12 / 对标

已有的尝试，以及它们各自的取舍

项目 / 产品做到了什么取舍 / 启发
Google Pixel Scam Detection端侧、实时、通话中主动出声提醒诈骗它敢做实时插话，是因为窄到极致——只判断"是否诈骗通话"，不做购物、不做会议、不做陪伴。这是"垂直换实时"最强的经验证据。

OpenClaw 类开源 agent能被 clone、能跑、社区自发传播带节奏的前提是可运行，不是文档漂亮。这是本文第 10 节的直接依据。

一句话收束：这个方向上，做"记录"的人很多，做"判定"的人很少，而判定才是这件事的全部难度所在。本草案不宣称解决了它，只宣称把它拆成了一个可以被验证的形式——一个 fixture、一个 schema、一个 precision 数字。
