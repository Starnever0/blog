1先说一个人人都会踩的坑

你大概经历过这个循环：听说某个新推理框架比手上这个快 25%，心动，准备迁。然后打开 README，一条条往下看——

只支持一个模型；只支持两种芯片；最小高效部署要 128 张卡；KV cache 系统、负载均衡、Prefill/Decode 分离这三块，没开源。

心动结束。

消息本身很硬：一个集群每天跑 155 万亿 token。但真正值得读懂的，不是这个数字，而是它摆在三家中间时的那条分界线。

2一句话说清它是谁

用后厨打个比方，三家角色就清楚了。后厨里的东西一一对应：炉灶刀具是 GPU kernel，厨师长排班是调度器，提前切好的半成品是 prefix cache，冷库是 KV cache 存储层，传菜员是负载均衡，前厅点单是 OpenAI API server。

3血缘确认：确实是 vLLM 带大的，但是“改装”不是“插件”

你的直觉没错。DeepInfer 的 README 致谢里写得很直白：

“DeepInfer was originally built primarily on vLLM, with additional inspiration from SGLang and TensorRT-LLM.”

翻译：骨架是 vLLM 的，灵感来自 SGLang 和 TensorRT-LLM。

但这里有个容易搞错的层次，值得掰开：

  • 骨架同源。调度器怎么排请求、KV cache 怎么分页、模型怎么加载、采样器怎么组织——这套 Python 层的结构是 vLLM 趟出来的。
  • 内脏全换。注意力、矩阵乘、专家通信这些真正吃算力的地方，换成了自家的 FlashMLA、DeepGEMM、DeepEP、DeepSelect、TileKernels，外加自己写的 TileLang kernel。
  • 所以它不是插件。你没法在 vLLM 上加个参数就切过去。它是一份独立代码库：共用图纸，但发动机、变速箱、空气动力学全部按一辆车重做。

顺带一个背景，能帮你理解这次开源的姿态。2025 年 4 月 DeepSeek 就想过开源完整引擎，当时放弃了，理由写在公告里——维护一个大型开源项目的工作量，超出了“一个专注做模型的小研究团队的承受范围”。

所以这次不是“我们终于想通了要拥抱社区”，而是“我们只开放引擎，不承诺社区运营”。这个姿态差异，后面会反复显形。

一句话收束：vLLM 卖的是“什么都能跑”，DeepInfer 卖的是“这一个跑得最快”。

这两句话不在同一个竞争维度上。所以“DeepInfer 打赢 vLLM”这种说法本身就不成立——它们不是同一类东西。

5真正的核心差异只有一条：用广度换深度

通用引擎的每一处设计都在为“兼容”付税。

为了同时支持几百个模型架构，kernel 只能做到“普遍都快”，做不到“对某个结构极限快”；调度器必须保守，不能假设“下一层的 attention 一定长这样”；KV cache 的分页粒度、块大小、淘汰策略都取折中值。

这不是能力问题，是定位问题——中央厨房不可能为一道菜改整条产线。

DeepInfer 把税免了，代价是只服务一道菜。只服务一个模型意味着它可以提前知道：专家的数量是多少、滑动窗口多大、MLA 把 KV 压成什么样、回溯长度上限在哪。于是能做出通用引擎结构上做不了的事。

两个只有“知道模型长什么样”才敢做的优化

其一，只重跑 prompt 的最后一段。DeepInfer 有个叫 SWA bounded replay 的机制，处理长输入时不再从头重算 decoder 层，只对 prompt 尾部一小段（V4.1 的默认设置是保留 140 个 token）重放，据官方说法能把 prefill 计算量近乎砍半。

为什么敢这么干？因为这个模型的注意力是滑动窗口的，更早的 token 本来就不参与当前计算。这个优化不是“更快”，是“知道可以不算”。通用引擎不敢做这个假设，因为换个模型假设就崩了。

其二，推测解码知道该信哪几个猜测。常规推测解码是“草稿模型猜 5 个 token，主模型全部验证一遍”。DeepInfer 的 DSpark 多了一层：用一个置信度预测头先估算每个草稿 token 被接受的概率，只把验证算力花在最可能被接受的那几个上。结果是验证的 token 数少了约三成，而平均接受长度几乎没掉。

这就是所谓的模型-引擎协同设计（co-design）。模型和推理引擎是一起设计的，很多优化写在模型的假设里，而不是写在框架的兼容层里。通用引擎抄不走这个，只能等模型开源之后追。

6和 SGLang 比：最像的那个对手

真正该拿来对照的其实是 SGLang，不是 vLLM。

对比项 DeepInfer SGLang
设计起点 为自己的模型做到底 结构化生成 + 高性能运行时
KV / 缓存策略 依赖外挂的 KV cache 系统（未开源） RadixAttention，前缀复用是看家本领，缓存感知调度
规模化 EP MoE EP + EPLB，decode 推荐 EP64 以上 DeepEP + EPLB + DeepGEMM 三件套，96 卡 H100 上能做到接近理论 EP 效率的九成
服务层 没有，自己补 完整，OpenAI 兼容 API、PD/EPD 分离、多 LoRA
生态位 DeepSeek 内部引擎的公开版 40 万+ GPU 上跑着，RL rollout（Miles / slime / verl / AReaL）的事实标准后端

为什么说它最像？因为两者押注同一个方向：DeepSeek 系超大 MoE + 大规模专家并行 + 前缀复用。在这条赛道上，SGLang 是过去两年最认真的那个外围追赶者。

它们真正的差别是闭环节奏。SGLang 是“你开源，我 Day-0 跟上”的外圈；DeepInfer 是“我先设计好，再决定公开多少”的内圈。内圈自然有信息优势——你见过模型的下一代，别人没有。

注意量级 这个优势是几个百分点的实现深度，不是数量级。而且 SGLang 现在也能跑 DeepSeek-V4.1-Flash，也支持 DSpark，也有 batch-invariant 推理（--enable-deterministic-inference）。DeepInfer 那份“独家功能”清单，剥掉宣传滤镜后其实比看起来短。

7一份第三方实测，和它顺带标出的价签

有人做了一次三方对照里最有信息量的实验：单机 8 张 B200，DeepInfer 与 vLLM 都用 DP8 + EP8，8K 输入 / 1K 输出，并发 16。

这组数据本身就是一次漂亮的对照实验，因为它同时量出了两件事。

吞吐赢，赢在生成阶段的 kernel 和调度更贴这个模型——这正是第 5 节讲的“深度”。

首字输，最合理的解释是缺了 KV cache 系统。8K 上下文的请求，每个都要从零 prefill 一遍；而 vLLM 有自动前缀缓存，重复的系统提示、工具说明、历史记录可以直接复用。

核心洞见 换句话说，那 2 倍的 TTFT 差距，就是“没开源那部分”的价格标签。

要提醒：这次测试配置没有针对性调优，DeepInfer 当时也没有 TP 路径、只能用 CP/DP 去对齐，所以这些数字不代表任何一方的上限，也不是官方数据。

8它凭什么快：四个动作

把散落的机制归拢一下，其实就四件事。

01

少算不该算的

SWA bounded replay，只重放 prompt 尾部一段。代价是它对模型结构有强假设，换个模型就失效。

02

少验不该验的

DSpark 的置信度调度。这里有个反直觉的细节：并发低的时候它是负收益（16 并发/rank 约 -1.5%），并发到 60 左右才赚 4%~7%。验证本来是投机生意——只有手上有一大批草稿可以挑，挑拣才有价值。

03

让 CPU 别闲着

异步调度，把排班和 GPU 执行重叠起来，默认开启。这类优化不惊艳，但在高并发下是持续漏水的桶。

04

把散装 kernel 缝成流水线

FlashMLA、DeepGEMM、DeepEP 这些库 2025 年就单独开源了。DeepInfer 的新东西是把它们和调度器、采样器编进同一条流水线，减少中间的数据搬运。

外加一件“听起来独家”的事

它还提供 batch-invariant 推理和确定性采样——同样的输入，不管这一批里还塞了什么别的请求，结果都一样。对做评测和回归的人来说这是真需求。

但这个想法不是它原创：vLLM 有 VLLM_BATCH_INVARIANT=1（beta），SGLang 有 --enable-deterministic-inference，源头是 Thinking Machines 开源的那套 batch-invariant 算子。DeepInfer 的贡献是把这件事在自家模型上做成了生产可用，代价是开确定性就得关掉 DSpark——可复现和更快，二选一。

9三个“没给你”的东西，才是真正的成本

README 里写得很客气，说一个完整推理服务还需要：KV cache 系统、VE/Prefill/Decode 分离、以及 DP 副本间的负载均衡。官方的解释是这三块和内部基础设施耦合太深。

这句解释是真的，但它只说了一半。另一半是：这三块才是成本优势的来源。

  • 那套 KV cache 保留策略——agent 流量留 3 天、聊天流量留 7 天，命中率 98% 以上，背后是 3FS 上约 100 PiB 的 SSD，每张在线 GPU 对应十来个 TB 的逻辑缓存。缓存命中率不是一个 kernel 能跑出来的数字，是一整套存储系统跑出来的。
  • PD 分离让读 prompt 和写回答跑在不同机器上，各自按瓶颈配资源。官方说的“最小高效部署”，是 64 张卡做 prefill 加 64 张卡做 decode。
  • 负载均衡决定这 128 张卡里有没有人在空转。

所以这句判断可以写进笔记：开源的是“怎么算得快”，没开源的是“怎么算得少”。

11要留心的地方

八条，按“最可能让你返工”的顺序排。点开看细节。

1只支持一个模型
而且是一个 2026 年 10 月 17 日刚发布的 checkpoint。模型一换代，你得等它更新。这条决定了它不可能成为你的技术底座，只能是一个研究样本。
2Hopper 系完全不支持
H100 / H200 / H800 不在支持列表里。这不是“还没适配”，是明确不在支持范围——官方只列了 SM100 和昇腾 950。手上只有 H 系列的话，连跑都跑不起来。
3昇腾路径零 benchmark
有代码、有构建路径、有独立依赖文件，但所有性能曲线都在 NVIDIA 上测的。代码对等不等于性能对等，这一点目前无人验证——任何“昇腾已追平”的说法都还没有证据。
4只有离线推理
没有 vllm serve 那种一行起服务的体验，OpenAI 兼容层要自己搭。社区已有第三方的 DeepInfer-server 这类封装，但那是别人写的胶水，不是官方产品。
5没有 TP 路径
只能靠 CP / DP 组织并行。跟别人做对比时，配置天然不对齐——上面那份 8 卡实测就是因为这个，被迫用 CP1/DP8 去对齐 vLLM 的 TP1/DP8。
6性能数字全是自测
155 万亿 token/天、每 GPU 每小时 38 美元这些数字来自公司公告，不是审计数据，也没说明是哪种卡、是收入还是利润。相对诚实的一点是：README 没做排行榜，只给了 Pareto 曲线和复现脚本。
7确定性相关能力仅限 NVIDIA
batch-invariant 和确定性采样都标注了 NVIDIA only，而且开确定性还要牺牲 DSpark 的加速。
8太新
首发 2026-10-20，距今两天。任何“生产可用”的说法现在都还只是承诺，不是记录。

12用一句话记住它

记住这一句
DeepInfer 是 DeepSeek 把自家后厨的门打开了：你能看到米其林怎么炒那道招牌菜，但冷库和传菜系统还锁着——所以你能学会“怎么算得快”，学不会“怎么算得便宜”。

再往上一层看，这次开源其实标出了一个正在发生的变化：开源正在从“给你一个能用的产品”变成“给你一份能读懂的实现”。前者省你的时间，后者省你的学费。这两件事的价值不一样，别混着算——读它，是为了少走弯路；用它，得先问问自己有没有那 128 张卡和那座冷库。

机制描述与功能清单依据 DeepInfer 官方仓库 README 及随代码发布的部署问答整理；vLLM、SGLang 的能力状态依据各自 2026 年 9 月版本（vLLM v0.30.0、SGLang v0.5.20）；第三方实测数据来自 GPUStack 社区的公开对照测试，非官方基准，仅用于说明架构差异的方向性影响。事实核对截至 2026-10-22，具体能力与版本以官方文档为准。
