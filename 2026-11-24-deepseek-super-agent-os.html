01 / BOTTLENECK
问题的起点

单任务的上限是模型，
多任务的上限是你

过去一年，Coding Agent 已经证明模型能用工具解决复杂问题，人的介入在不断后移。 但主流 Agent 仍然以「一次会话」为工作单位：不同会话彼此独立，你要并行推进， 就得自己切换、自己记住前情、自己搬运上下文。

DeepSeek Harness 团队给出的观察很朴素：一个人通常只能同时跟进 3 到 5 个活跃会话。 超过这条线，你的时间不是花在思考上，而是花在「这个窗口进行到哪了」上。

于是出现一个结构性矛盾：AI 越能干，你越忙。你打开五六个窗口， 每个里面都有一个 AI 在干活，而你成了那个负责调度、切上下文、判断优先级的 CPU —— 一个只有单核、还会累的 CPU。

模型能力决定单任务的上限，人的注意力决定多任务的上限。 — Exploring Super-agent Design 的核心判断

为什么在单会话上打补丁没用

  • 阻塞
    同步阻塞。一个长测试跑十分钟，这十分钟里你没法给它新指令。
  • 污染
    上下文串味。一个任务的日志越堆越多，另一个任务的判断精度跟着下降。
  • 停机
    设备即生命周期。笔记本合上，任务就停了；进程重启，会话就散了。
  • 人力
    靠人维护。CLI、MCP、连接器能扩能力，但扩不了「谁记得住」。

02 / CORE IDEA
它到底是什么

一个跨会话、能并行、
会自己找活干的常驻实体

Super-agent 不是更强的模型，也不是更长的上下文。它是一个系统形态： 用户面对的始终是一个助手，系统背后同时开着若干个互不干扰的执行单元， 而「会话」退回成实现细节 —— 就像你不需要知道进程被调度到哪个核上。

论文给了一个很克制的定义，四个词：Continuous（连续）、Efficient（高效）、 Proactive（主动）、Persistent（持久）。这四个词不是形容词，是四条硬指标 —— 每一条都对应一个必须解决的工程问题。

关键的一刀切在这里：把「管理模型上下文」和「管理人的项目」拆开。 过去一个 Session 同时干这两件事，所以人被迫用 Session 来组织工作。 拆开之后，人只管目标和验收，调度交给系统。

会话成了实现细节。让用户去管理会话，是从底层 LLM API 继承下来的习惯。 — 论文对 Session 作为工作单位的批评

四个特征，四道工程题

连续 CONTINUOUS

群聊里定方案 A，PR 评论里改成 B，它跟得上。不用你复述前情。

↔ 单一地址空间

高效 EFFICIENT

多个复杂任务同时推进，一条耗时任务不阻塞你发下一条指令。

↔ 多进程并发

主动 PROACTIVE

持续观察环境事件，值得处理才行动；不需要的时候保持安静。

↔ 中断 + 过滤器

持久 PERSISTENT

设备离线也不停，进程挂了能自己恢复。状态比进程活得久。

↔ 存算分离 + 看门狗

最不性感、也最重要的一点：它不发明理论

团队自己说得很清楚：这不是一套全新的理论。调度、缓存、隔离、快慢路径、存算分离、看门狗， 全是操作系统和分布式系统里被验证过几十年的东西。它做的事情是重新组合 —— 把「怎么让多个任务在有限资源上互不干扰地推进」这件事，从人的脑子里搬回机器里。 所以你在这套架构里看到的每一块，几乎都能在 OS 教材里找到原型。这也是下面那张对照表的由来。

03 / MAPPING
核心对照

十二张卡，看懂它在抄谁

这套架构最值得学的地方，不是某个模块，而是「遇到并发、隔离、状态、故障时，先问 OS 怎么做」。 下面每一对都是同一道题的两种解法：左边是被验证了四十年的机制，右边是它在 Agent 里的对应物。 点开任意一张看细节。

两种视角只换重心，不换内容
OS
进程调度器
process scheduler
↔
SUPER-AGENT
Router / Worker 双层
router dispatches, workers run

Router 只决策，Worker 只执行。Router 承接所有人类交互、维护全局上下文、判断这活派给谁；它自己不做活，甚至可以不给它 Bash 工具，跑个轻量模型就够。Worker 拿到任务后在自己的上下文里干，配上完整工具链和最强的模型，但不直接对人说话——中间过程和报错都留在里面，只把结果汇报给上层。

并发不是无限的：原型用 WorkerSlots 卡住同时在跑的数量，超了排队；人发来的消息可以额外占用一个保留槽，保证它永远不会排在新任务后面。

收益连续性和吞吐第一次不用二选一
OS
地址空间隔离
address space isolation
↔
SUPER-AGENT
每票一个会话 + 一个目录
one session, one worktree per ticket

每个 Ticket 开一个独立的 Session、一个独立的目录，通常用 git worktree 拉一份干净检出，路径按工单 ID 命名。这样一个任务几百行的执行日志、几次失败的尝试，都不会污染另一个任务的判断。

这一点比看起来重要：单会话 Agent 的能力衰减，很多时候不是模型变笨了，是上下文里塞满了上一个任务的残渣。

注意原型的隔离是「默认值」，不是安全边界（见第 08 节）
OS
页缓存与换页
page cache · swap
↔
SUPER-AGENT
Inline & Spill + 链式召回
context window as a cache

把上下文窗口当缓存用：窗口是快的、小的；SQLite 是慢的、大的。Inline 是把还需要的信息载进窗口；Spill 是把它换出去，只留一个 ID 加 50 字符的摘要桩。需要时按 ID 再走回来——这叫 Chain of Recall，本质就是页表的指针追逐。

局部性策略很直白：近期 Thread / Ticket 的消息留在窗口里，久远的、弱相关的换出去。原型里 Trigger 正文硬上限 4000 字符，超出就截断并给读取指针。

权衡模型 token 便宜但快，工具读取慢但准
OS
中断控制器
interrupt controller
↔
SUPER-AGENT
Trigger 事件流
events, not prompts

工作不再靠人逐条输入提示词，而是由事件触发：群聊消息、邮件与日程提醒、PR 评论、CI 运行结果。它们统一叫 Trigger——不可变、可幂等（同一个 Trigger 接两次只建一个 Ticket），这既是审计单位，也是「重启不重放」的保证。

平台差异被 Source 插件吃掉了：GitHub 的通知、飞书的话题消息，都被翻译成同一种 Trigger，内核不需要知道对面是哪个平台。

关键没有 @ 它，也能开始干活
OS
中断上半部 / 下半部
top half · bottom half
↔
SUPER-AGENT
Gate（代码）+ 研判（模型）
fast path · slow path

绝大多数群聊消息不需要 Agent 介入。所以事件进来先过一层确定性过滤（Gate）：来源对不对、在不在白名单、是不是同一个话题、有没有 @ 到它。这一步是代码，零模型成本。

只有过了这一层的候选，才交给模型做语义研判（Assessment），判断这是不是真的在要它干活。便宜的判断先做、贵的判断后做——这是中断上半部和下半部的关系，也是所有高性能系统的老套路。

实现Fast Path 是代码，Slow Path 是可用 prompt 配的自然语言规则
OS
定向信号 / 进程间通信
directed signal · IPC
↔
SUPER-AGENT
Thread 订阅直通
subscription pass-through

Worker 接手一个 PR 之后，会订阅这个 Thread。之后这条 Thread 上的新评论直接投给它，不再经过 Router 转发。这既省调度开销，也省一次上下文重建。

论文做了消融，把这个机制关掉：Router 的决策次数涨了大约 30%，read-cache token 从 23.23M 涨到 31.77M，多了约 37%。所以直通不是锦上添花，它直接改变了成本结构。

一句话谁负责这件事，后续信号就直投谁
OS
fork / 子进程
fork · exec
↔
SUPER-AGENT
Worker 派生子 Agent
subagents, transparent upward

Worker 内部可以再开子 Agent，把一个大任务拆开做。这一层对 Router 完全透明——Router 只负责任务之间的派发，不负责任务内部的分解。

这也是它和 Agent Teams 的区别：Teams 分解的是一个紧耦合的复杂任务，Lead 的协调很重；Super-agent 的 Router 把「团队负责人」压缩成只对外交互和派单，于是同一个模式可以在任务间无限复制。

实验单会话 Agent 在 5 次中性提示下，一次都没有主动委派子 Agent
OS
作业控制
job control · SIGSTOP / fg / bg
↔
SUPER-AGENT
异步 ReAct（start / stop）
full-duplex interaction

经典 ReAct 会阻塞在工具执行上：命令跑十分钟，这十分钟里模型什么都干不了，也听不见你说话。改成全双工之后，工具调用变成异步的 start() / stop()：模型立刻拿到一个「已启动」的句柄继续思考，工具完成时作为一条新事件回来；长命令也可以中途喊停。

新输入在当前推理步之后就被处理，不用等后台工具跑完。这个机制在 DeepSeek Harness 里已经实现，但默认没有打开。

体验差异以前是「提交-等待」，现在像「说话-打断」
OS / 分布式
存算分离
compute-storage separation
↔
SUPER-AGENT
计算 / 状态 / 执行 三层
cloud loop · sqlite · BYOM daemon

三层各管一件事：计算是无状态的 Agent Loop，跑在云容器里，挂了重启就行；状态是独立的持久库（原型用 SQLite），是唯一事实源；执行是本地机器上的一个轻量 daemon（BYOM，Bring Your Own Machine），只负责执行命令，不做任何推理。

所以合上笔记本，任务只是暂停，不是销毁；换台机器接着跑也行。代价是引入网络延迟，并且状态层变成必须做高可用的关键单点。

对应无状态计算节点 + 远程块存储 + 本地设备
OS / 硬件
看门狗定时器
watchdog timer
↔
SUPER-AGENT
独立的 Watchdog 会话
fault detection outside the faulty part

原则只有一句：故障检测不能跑在故障组件内部。所以 Watchdog 是一个独立的会话/进程，不是 Router 里的一段代码。它从两个面看：基础设施面（进程还活着吗、队列积压吗）走确定性判断；语义面（这个 Worker 是不是在原地打转、目标漂移了没有）走独立的模型判断。

心跳的含义也很具体：Worker 必须汇报实质性进展。反复调用同一个工具、结果没有变化，就算卡住。补救措施分等级——硬故障自动重试，语义软故障先告警，破坏性操作必须人确认。

原型现状只有心跳板和副作用重试，独立巡逻会话尚未实现
CPU
投机执行
speculative execution
↔
SUPER-AGENT
静默复现并修复
silent reproduce & fix

有人在群里反馈一个 bug，Agent 先在后台复现、定位、试一个简单修复。确认问题存在、且修复足够简单，才提交；否则保持安静，不打扰任何人。

这是把 CPU 的投机执行搬到了 Agent 上：结果会不会被采用还不确定，但先算的成本很低，算对了就省掉一整轮往返。个人助理场景同理——收到会议邀请，先把日程核对、资料整理、回复草稿都备好。

前提失败必须无副作用，所以「只记录不提交」是默认档
OS
系统调用与权限
syscall · capability
↔
SUPER-AGENT
Mandate 授权票据
a unit of authorized work

一次「接单」不只是说一句好，而是签发一张 Mandate：策略版本、工作范围、授权强度（明确要求还是推断出来的）、命中的规则、发起人在该平台上的身份。它不可变——范围要扩大，就得开新工单。

撤销权只在人手里：人喊停，授权作废；策略变了，授权失效。工单结束不等于授权结束；工单要恢复，必须按当前策略重新校验一遍。

诚实说原型里这道边界只到调度器，Worker 的 shell 仍以操作员身份运行
操作系统侧 Super-agent 侧 ↔ 不是比喻，是同一类问题的同一类解法

还有三条，藏在实现里

日志 / journaling → Effects 队列

所有对外副作用先入持久队列，提交后才执行，失败指数退避，保证至少一次投递。进程崩了，欠的账还在。

GitHub、飞书各自实现一套「怎么读事件、怎么回消息」，内核只认 Trigger 和 Channel。换平台不用改调度。

单一写者 / 内核态 → Engine

Trigger、Thread、Ticket、Decision 只有一个写入者，全部命令走同一个事务入口。状态只有一个人能改，才不会互相踩。

06 / MEMORY
缓存这一课

上下文窗口不是仓库，是缓存

一个跑了几天的 Agent，历史记录远大于窗口。绝大多数系统的做法是「截断」—— 把最旧的扔掉，扔掉的可能正是关键约束。Super-agent 的做法是把它当页缓存管： 热的留在窗口，冷的换出去但留一个地址，需要时按地址追回来。

Inline 就是把一条消息载进上下文窗口；Spill 是把它换出去， 但在窗口里留一个 50 字符的摘要桩和它的唯一 ID。模型看到这个桩，知道「有这回事」， 需要细节时再按 ID 去读原文。

Chain of Recall 是这套东西的关键：ID 之间互相引用，形成一张图。 你从一个桩跳到原文，原文里又引到另一条记录，可以一路追下去——这就是页表的指针追逐。 代价是每次追都是一次工具调用，比留在窗口里贵得多。

所以策略不是「尽量少占窗口」，而是按局部性决定谁留谁走： 当前的 Thread、正在做的 Ticket，留在窗口；三个月前的会议记录，换出去。 原型里的硬指标是 Trigger 正文最多 4000 字符，超出截断并给指针。

弱局部性会让这套机制变贵：如果你总是随机跳回很久以前的历史， 工具读取的开销就会盖过省下来的 token。 — 论文自己列出的边界

为什么 Loop 必须无状态

有状态就没法随便重启、没法迁移、没法横向扩。把「记得什么」交给库，循环本身就成了可丢弃的。

为什么执行必须留在本地

代码、未提交的改动、凭证都在你机器上。云端不需要拿到这些，只需要发一条命令、收一个结果。

为什么 daemon 只执行不推理

一旦本地也跑推理，它就成了第二个大脑，状态会分裂。它只能是一个手，脑子只有一个。

一个反直觉的结论：负载越高，单位成本越低

触发率从每分钟 1 次涨到 40 次，批处理把多个 Trigger 合并成一次决策， 平均批大小从 1.0 升到 2.8。结果是单次决策的推理时间从 6.4 秒降到 1.6 秒—— 虽然消息延迟从 2.5 秒升到 3.9 秒。

这就是「合并就绪队列唤醒」在 Agent 上的版本：攒一批一起判，比一条一判便宜得多。 代价是最后一条消息要多等一会儿。系统选择了吞吐。

现在说不好的部分

这套架构被讨论得最多的不是它有多强，而是它的边界在哪。下面这些不是「未来会更好」的客套话， 是作者和外部评审都点出来的具体缺口。做技术选型时，这些比性能数字更重要。

01

隔离是默认值，不是安全边界

README 写得很直白：阻断命令、每工单独立目录「establish defaults, not a security boundary」——Worker 仍然可以用绝对路径执行程序。而它是以操作员的操作系统用户身份跑 shell 的。自动接收不可信事件 + 高权限执行，这是个危险的组合。合并条件也只是 prompt 里的指令，真正的审批得靠分支保护。

02

Prompt injection 只是被约束，不是被阻止

来源过滤、白名单、授权表能降低概率，但事件是从 GitHub 和聊天里自动流进来的，攻击面天然开放。论文自己的措辞是 constrain 而不是 prevent。任何把它接到公开仓库上的部署，都得先想清楚这一层。

03

Router 是一个单点

所有人类交互都过它，所有跨任务判断也在它这里。要往上扩只能做分片调度，而分片就会牺牲一部分「全局只有一个 Agent」的连续性。这是设计里没有免费午餐的地方。

04

看门狗自己也会坏

「谁监控监控者」没有彻底答案。所以补救措施必须保守：破坏性操作默认只告警，人工确认才执行。这意味着它不是一个能完全放手的系统。

05

省的是注意力，花的是钱

cache-read token 23.2M，对比单会话的 6.1–10.8M，大约是 2–4 倍。这笔账划不划算，取决于人的时薪和任务等待的成本。对个人开发者，可能不划算；对一个每天被几十条 review 淹没的团队，可能很划算。

06

论文 ≠ 原型

异步 ReAct 在 Harness 里实现了但默认关闭；独立的 Watchdog 会话原型里没有，只有心跳板和副作用重试；长期跨月记忆、A2A 通信、组织级权限都还在开放问题里。作者明确说有些设计是未来方向。

07

它是研究原型，不是产品

README 第一句：reference only, not an official DeepSeek product。相当一部分代码是 coding agent 自己写的，作者自己说可能有 bug、风格不一致。拿去用之前得自己审一遍。

09 / GLOSSARY
概念速查

看论文前先认这十几个词

这套文档有一个很好的习惯：只保留工作真正需要的概念，业务需求变成某个概念的属性， 而不是新增一个概念。所以词表不长，但每个词都有明确的规则。

Super-agent系统形态
跨会话连续、并行处理多任务、主动响应环境、长期在线的 Agent 实体。不是模型，是架构。
Harness运行框架
承载 Agent 的运行时，DeepSeek 在 2026-08 以 MIT 开源（dsh），设计哲学是「一切皆插件」。Super-agent 原型是它的一个 bundle。
Router调度层
常驻的全局协调节点。承接所有人类交互、维护全局上下文、判断任务派给谁。它不做具体工作，可以没有 shell 工具，用轻量模型就够。
Worker执行层
隔离的执行单元。一个任务一个上下文、一个目录，配完整工具链和最强模型。不直接对人说话，只向上汇报。
Session会话
一次连续的模型交互上下文。在 Super-agent 里它退化成实现细节，不再是用户组织工作的单位。
Trigger触发
一个不可变的输入事件，带来源元数据（谁发的、在哪个平台）。幂等：同一个 Trigger 接两次只建一个工单。是审计和去重的单位。
Thread线程 / 话题
按时间排列的一组 Trigger，由 Source 定义什么算同一条 Thread（一个 PR、一个群话题）。同一条 Thread 上同时只跑一个 Eval。
Source来源
事件流的抽象。一种 kind 是可复用的实现（GitHub、飞书），一个 instance 是一份配置（监听什么、用哪个账号）。它负责把平台消息翻译成统一事件。
Gate准入
Eval 的第一层，确定性代码：谁有权发起工作、以多强的依据、有没有在白名单里。零模型成本，挡掉绝大多数噪音。
Eval / Assessment评估 / 研判
Eval 是把一批 Trigger 变成一个 Decision 的过程；Assessment 是其中由模型做的那部分语义判断。注意它不持有状态。
Ticket工单
一个「已授权的工作」单位。只有 Eval 能创建。它有自己的生命周期（open → ended → 可被人的消息恢复），不跟随执行器的状态。
Mandate授权
接单时签发的东西：策略版本、范围、强度、命中的规则、发起人身份。不可变；扩大范围要开新工单；只有人能撤销；恢复前要按当前策略重新校验。
Assignment派工
工单和某个执行器实例的绑定。一个工单一生可以有多次派工，每次独立地 pending → running → ended。
Subscription订阅
工单和 Thread 的多对多关系。订阅之后，该 Thread 的新消息会直接扇出给这个工单，不再走一遍全局判断。
WorkerSlots并发配额
同时运行的 Worker 数量上限，超了排队。人发来的消息可以额外占用一个保留槽，保证它永远不排在新任务后面。
Inline & Spill上下文缓存
把上下文窗口当缓存：需要的载入（Inline），不需要的换出但留 ID + 50 字符桩（Spill）。对应 OS 的 page in / page out。
Chain of Recall链式召回
对象 ID 之间互相引用形成的检索链。从一个桩跳到原文，再从原文跳到下一条记录。对应页表的指针追逐。
BYOM自带机器
Bring Your Own Machine。本地开发机上跑一个轻量 daemon，只执行命令、不做推理，持有代码和凭证。设备离线时任务暂停而不销毁。
Watchdog看门狗
独立的监控会话/进程，不参与实际工作。靠心跳判断 Worker 是否真在推进。核心原则：故障检测不能跑在故障组件内部。
投机执行Speculative
结果还不确定时先在后台算。典型策略「静默复现并修复」：确认能简单修好才提交，否则保持安静。
ReAct推理-行动循环
Reason + Act 的循环范式。经典实现是同步阻塞的；Super-agent 把它改成异步 start/stop，实现全双工交互。
Worktree工作树
git worktree，同一个仓库拉出多个独立检出目录。原型用它给每个工单一份干净的工作区，互不干扰。

一条值得记住的设计规则

「一个概念只有一种写法，一种状态只有一个写者。」 这套系统里，Trigger、Thread、Ticket、Decision、Assignment 全部只能由 Engine 写； Source 只能通过两个命令间接改工单。听起来像洁癖，但这是它能被调试、能被回放、能重建状态的前提。

如果你要自己搭一套

  • 先做
    把「输入」和「执行」拆开。哪怕只有一个 Worker，先让调度器不干活。
  • 再做
    给每个执行单元一个干净的目录和上下文。隔离带来的收益比并行更早出现。
  • 然后
    把所有状态放进一个库，让循环可以随时被杀掉重启。
  • 最后
    加监控，但别让它跑在被监控的进程里。
  • 别急
    先别做主动性。默认「只记录不执行」，等你确认它想做的事对，再放开。
